# ADR 0015: Bounded API execution, database reuse and shorter budget locks

Status: implemented for review; no staging/production deployment or capacity approval.

## Problem and evidence

The historical five-device, all-nine-recipient stress workload includes about 400 authenticated HTTP requests/s and 180 durable recipient copies/s at 20 new messages/s; this is an explicit heavy stress case, not an ordinary per-user device assumption. One native crypto worker was a serialization point, but earlier controlled trials did not identify it as the dominant limit. Further investigation reproduced a slow WebSocket authentication query blocking unrelated sessions through a shared executor, and a delayed message/outbox insert blocking an unrelated account through the global StorageUsage service-row lock. Query construction, redundant nested savepoints, read transactions and repeated physical database connections add work to this path. Evidence, failed hypotheses and capacity limitations are recorded in the [throughput investigation](../security/metadata-privacy/throughput-fixes.md).

## Decision

Use `python -m haven.server` in both API images and local development. It starts four Uvicorn processes by default. `HAVEN_API_WORKERS` accepts 1–8; each process defaults to a pool of `min(16, 64 // workers)`. `HAVEN_DB_POOL_SIZE` can override that size within 0–32, but the aggregate configured pool budget cannot exceed 64. Supplied Compose defaults are explicitly 4/16: changing them requires selecting both values within that bound. This leaves space under the existing PostgreSQL 100-connection limit for maintenance, outbox, health checks and operator work. The pool budget applies to one active API deployment; operators must include replicas/standby and other processes in the complete database budget. Size zero is an explicit diagnostic opt-out, not the qualified default.

ASGI uses dedicated `haven.runtime_settings`; management and migration commands retain non-pooled base settings. Runtime pools have zero Django persistent-connection age, live checkout health checks, a three-second timeout, 64 maximum waiters, 60-second idle expiry and 600-second connection lifetime. Server-side binding keeps values separate from SQL text. It does not hide a query's tables or relationships from a privileged database/live-server observer, erase connection memory, or add anonymous authority. Pool diagnostics remain suppressed. Real SQL failure rolls back; transactions are not replayed automatically. HTTP authentication availability failure returns generic 503; WebSocket database failure closes 1013 and removes transient links.

WebSocket database functions use eight bounded, independent worker threads per API process. Each function opens/uses/closes its own connection, returns primitives, and preserves Channels cleanup. No ORM connection crosses threads, no session or permission verdict is cached, and every frame/hint still checks live authority. Channels' ordinary dispatch lifecycle remains intact.

The fixed parameterized authentication query preserves the original fourteen-field projection, current expiry/revocation/active-account predicates, password-derived HMAC comparison, deferred model fields and related-object identities. Explicit concrete-field ordering handles inherited User and auto-created Session fields. Protected reads still refresh authority; protected writes retain sorted account fences and post-lock refresh. Read-only handlers avoid an unnecessary write transaction; view-once chunk reads retain their explicit transaction/locks. Mutating handler decorators join the outer request transaction without redundant savepoints. Inner savepoints used to recover from actual integrity errors remain.

Read membership/conversation lookup uses one join and the freshly authorized device. Message/control membership lookup retains conversation-lock-then-member-recheck order; a locking join could use a stale membership snapshot after waiting. Existing ACK cursors select only their sequence, remain monotonic, and duplicate/idle ACKs perform no UPDATE. ACKs retain the outer actor-account fence, which serializes credential/device changes and targeted membership removal. They read membership/head together, update only their own cursor, then acquire the conversation row through the final atomic receipt-version increment. Heads advance monotonically; no other application writer takes a cursor lock before its account fence. Retirement reads committed cursors and cannot use an uncommitted ACK to erase ciphertext. This shortens the conversation critical section while preserving account authorization, monotonic cursors and exact version increments. Other mutating membership reads still lock the conversation before refreshing membership. Signature, quota and failure gates stay effective.

For ordinary sends, insert the conversation head, envelope and outbox before acquiring storage-budget locks. These changes are uncommitted and invisible; budget rejection rolls them all back. Lock account/service budget rows in the existing order, check every existing limit, then apply identical deltas with one UPDATE. This shortens the global service-row critical section without sharding its limit, admitting overdrafts, dropping events or weakening synchronous commit. Control-event writes still finish in the same outer transaction.

The notification publisher owns a dedicated Channels backend and one asyncio loop throughout the command lifetime, allowing Redis connections to be reused. A batch claims up to 100 existing outbox rows with `skip_locked`, queries the same current membership predicate once, and emits one coarse sync hint per eligible account. Only successful notification of every target marks all claimed rows sent, with one update; a partial failure rolls the transaction back, preserving retries. Hints carry no conversation or message identity. Clients still revalidate live authority and retrieve durable envelopes over HTTP. Nonempty batches drain without an extra fixed delay; empty/failing iterations pause 0.5 seconds. Tests exercise actual PostgreSQL, Redis and authenticated sockets, including unrelated-account exclusion and a partial-send failure followed by retry.

The revised default synthetic generator follows the [workload plan](../security/metadata-privacy/workload-plan.md): 100 people, two trusted devices each, 120 initially connected identities, mixed direct/five-person conversations and independent recipient queues. The 20/s burst, steady endurance, handoff, intermittent, multiple-tab connection and group fan-out cases are explicit. Each device verifies, fsyncs and cumulatively ACKs ordered history without a cross-recipient send barrier. Two bounded native authors per conversation release the publication lane after acceptance and sender checkpoint while retaining each author’s own lock through its ACK; a different author need not wait for that ACK. Actual native held-ACK controls verify the dependency removal, and complete-intent deadlines remain unchanged. Returning devices catch up before authoring; no pending send intent is dropped. The prior 500-identity/all-nine-recipient barrier remains available under `--profile legacy-stress`, with zero recipient workers preserving its serial control. Every offered event drains, and the ten-second unfinished-work and zero-socket-error gates stay intact. Disabling API phase timers is an explicit measurement control, not a security bypass.

## Alternatives and limits

Pool-only, eight-process, WSGI adapter/thread-count and direct synchronous-server experiments are retained as diagnostics. Experimental HTTP servers are not promoted merely because one failed workload drains faster. The production HTTP/WebSocket router remains Django/Channels ASGI. Temporary diagnostic packages are not runtime dependencies.

No schema, identity, browser storage, MLS/signature/wire format, public response contract, rate/storage limit, ingress trust rule or durability setting changes. `CRYPTO_READY=False` remains the normal source gate. Existing migrations and coordinated upgrade safeguards still apply. More processes and retained connections increase bounded steady memory; the shared workstation cannot establish reference-production capacity, mobile behavior or independent security assurance. Performance qualification requires completion of the applicable burst and endurance scenarios on a qualified reference host; a drained overload is not that evidence.
