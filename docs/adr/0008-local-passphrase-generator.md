# Optional local unlock-passphrase generation

Status: implemented; local engineering tests recorded in TEST_REPORT.md. Independent security/release gates remain unchanged.

The owner requested an optional generator on the guided new-browser setup screen. Existing-vault unlock must never offer to replace its protecting secret or regenerate its identity.

- An explicit click draws 32 bytes with the browser's `crypto.getRandomValues` and losslessly encodes them as 43 base64url characters. No new dependency, remote service, word list or messaging cryptographic protocol is introduced. This relies on the browser/OS CSPRNG; it is not an independent assessment of its entropy source. Reference: [W3C Web Cryptography, getRandomValues](https://w3c.github.io/webcrypto/#Crypto-method-getRandomValues).
- Generation is available only after storage confirms that no vault exists and the existing setup gate is open, on a secure browser context with a functioning random source. Failure never falls back to Math.random, timestamps, UUIDs, usernames or predictable words. Manual passphrase entry retains the existing minimum-length and confirmation requirements.
- Generated values are masked by default. Reveal and clipboard copying require deliberate actions. Clipboard denial offers manual reveal/copy; it never reveals the secret automatically. Copying does not automatically check the user's saved confirmation. Regeneration and switching to manual entry clear the confirmation; leaving the setup discards the unsaved React state.
- Creating a vault with a generated secret requires revealing or successfully copying it first, followed by an explicit saved confirmation, enforced in the submit handler as well as the button state. Generation alone never enrolls a device, saves a plaintext value, initializes a messaging identity or sends the secret to an API. Existing Argon2id/AEAD vault protection is unchanged. Interrupted creation preserves its existing encrypted vault and resumes as unlock.
- There is no automatic plaintext download or server-side password retrieval. The user can record the secret privately or save it using their own password manager. This local unlock secret is separate from the account password and the encrypted recovery kit's key. Losing it requires the pre-existing recovery workflow and appropriate recovery material; generating another value cannot unlock old ciphertext.
- Temporary random byte buffers are cleared after encoding. Immutable strings, React/browser/extension/decoder memory, screenshots and OS clipboard history/synchronization cannot be guaranteed erased. Deliberate copying leaves the clipboard under OS/user control; the app does not overwrite it later or silently erase unrelated clipboard content. A compromised origin/browser/extension can steal generated or manually entered secrets. Masking is protection against incidental viewing, not a cryptographic boundary.

Tests cover known byte-to-text encoding, CSPRNG failure without an insecure fallback, reset/confirmation/copy/reveal states, explicit clipboard-denial recovery, generation cancellation, real encrypted-vault creation and unlock after reload, no generated value in observed request URLs/bodies or plaintext local/session storage, encrypted IndexedDB records, unchanged identity, existing-vault exclusion, source gate and responsive EN/FA views. These are local desktop-browser checks, not independent security verification or physical iOS/Android qualification.
