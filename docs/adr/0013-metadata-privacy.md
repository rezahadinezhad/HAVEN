# ADR 0013: minimize retained metadata; keep authenticated routing until a reviewed replacement

Date: 2026-11-02. Status: implemented bounded hardening; advanced routing research only. Baseline: `0240706` / PR #18. Production qualification unchanged and blocked.

## Decision

Remove `Session.last_seen`, `DeliveryCursor.updated_at`, `AttachmentChunk.stored_at` and the unused DeliveryReceipt model/table. Durable cursors already derive receipt state without recording individual receipt times. Remove server acceptance time from envelope serialization and corresponding contracts; the server keeps the time needed by retirement/aggregate queue health. Let KeyPackage.device become NULL after expiry and scrub it together with payload, claimant and consumed time, including legacy rows whose payload is already empty. Retain digest, ID, expiry and version fields to reject reuse.

Project the outbox worker onto its necessary envelope ID/conversation only. Recheck abandoned-upload deletion after taking the same row lock as completion/view operations. Record an aggregate unavailable maintenance status after a failure; do not leave a fresh cached success. No identity, exception, content or path is added to that status.

Use OpenMLS 0.9.2's RFC 9420 PrivateMessage padding with a 256-byte block in new create/join configuration. Upgrade the adapter's exact legacy default configuration at the first new encryption, with unknown configurations failing closed. This preserves the existing secret-retention policy rather than rebuilding arbitrary state. The API still accepts valid unpadded old-client messages. No protocol/vault version bump, ratchet reset, dummy-traffic loop, attachment padding or endpoint-anonymity claim.

Redis account-to-channel group associations now expire after 120 seconds rather than the library default of 86400, and only authenticated incoming frames renew or restore them. Redis failure closes that WebSocket for reconnect; HTTP remains authoritative.

Every candidate is evaluated across confidentiality/integrity, metadata, MLS compatibility, unauthorized access, abuse, ordering, recovery, multi-device, migration, operational complexity, throughput/latency and network observers. The [research specification](../security/metadata-privacy/routing-research.md) makes unresolved requirements explicit. Do not add an apparently anonymous bearer endpoint that bypasses membership, signed order or accounting.

## Key custody and encrypted metadata

Existing E2EE message/media/vault keys are endpoint-held. Database auth hashes and rate-label HMACs use the server secret; secret rotation invalidates sessions/rate labels and is not MLS identity rotation. Server storage encryption or AEAD metadata under an always-online key protects only attackers without that key. Client-assisted encrypted graph storage could withhold keys between requests, but asynchronous delivery, all-device ACK eligibility, revocation and quotas currently require membership access while recipients are offline. A new protocol is needed before that is safe. Randomized authenticated encryption is necessary for a future encrypted field, but alone does not remove index, length, access-pattern or signed-proof duplication.

## Narrower field-encryption alternative

Encrypting account usernames/display names under a separately held server data key could reduce **labeling** of an A1 graph even though it would not remove its edges. That narrower benefit is distinct from hiding the graph and must not be dismissed because signed history still contains UUIDs. It is not implemented in this change. A compatible design needs purpose-separated normalized login lookup tags, authenticated row/field/version binding against swaps, key IDs, overlapping key rotation, fail-closed missing-key behavior, protected backup/restore custody, uniqueness and Django authentication/admin serialization migration. Reusing SECRET_KEY without an independently specified rotation/restore plan would couple account availability to an unsafe migration. A4 still obtains decrypted labels and lookup inputs. This remains a separately reviewable storage/authentication migration; this report does not claim labels are encrypted or that every possible metadata reduction has been exhausted.

## Compatibility and costs

0014 adds an expiry/ID partial index on non-scrubbed KeyPackages; cleanup orders by those columns so permanent tombstones leave the cleanup index.

0013 is an offline coordinated migration, not mixed-version server rollout. Removed metadata cannot be reconstructed by reverse DDL; the migration refuses reversal. Existing tokens, cursor seqs, view-once leases/consumption, signed proofs, quotas and pending ciphertext remain. Browser snapshots retain schema v1; OpenMLS local config upgrades without touching epoch/ratchets. Bounded padding adds zero through 255 content bytes, with possible additional MLS vector-length encoding bytes; Base64, JSON, TLS and HTTP add their own framing. Existing transactional quotas charge the actual padded ciphertext bytes; capacity can be reached sooner, and pending exact ciphertext must remain retryable instead of being discarded or re-encrypted to fit. Native measurements are explicitly not production latency/capacity qualification. No new dependencies or foreign runtime requests.

## Review and evidence

Field coverage, actual synthetic dump/restore and failure/retry checks, PostgreSQL concurrency/query/API tests, native/WASM tests, full browser suites and primary-source analysis are linked from [the report](../security/metadata-privacy/report.md).
