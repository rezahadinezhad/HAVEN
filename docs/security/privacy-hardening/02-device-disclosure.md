# Device disclosure containment

**IMPLEMENTED_AND_TESTED.** Previously `KeyPackages.get` returned any approved active target by UUID; claim also accepted UUID knowledge, returning label and enrollment challenge/approval relations alongside the certificate. An authenticated unrelated approved user could inspect known IDs and reserve packages without an introduction.

`apps/api/core/views.py` now separates own enrollment `device_json` from `peer_device_json`. Peer/roster/claim responses contain exactly id, user_id, identity, public_key, trust_state and revoked_at. Own device/enrollment endpoints retain challenge, approved_by, approval_signature and label so existing-device approval still verifies. Admin device listing was already minimal and is preserved. Admin account listing has its own four-field contract. OpenAPI, generated TS types and frontend consumers were updated together (`scripts/generate-contracts.py`, `packages/contracts`, `src/lib/generated/schema.ts`, `api.ts`). Peer roster reads and first-contact claim joins also project only required fields, including only target account is_active rather than its password/profile. Advanced/manual lookup accepts a scoped friend link and preserves independent fingerprint verification.

Lookup requires own account, shared historical membership, or an explicitly shared 24-hour introduction. Historical membership remains sufficient for the public certificate of revoked or inactive peers: history verification must not depend on their current account access or an unexpired link. Claims require an active approved target plus own account, a current active shared relationship or introduction. They still do not authorize Add, bypass fingerprint pins, approve devices or create membership. Target-account mutation fencing serializes claims against completed revocation/link-generation changes; existing sorted account-lock ordering is preserved.

Unknown/unauthorized/inactive-unrelated UUIDs return the same 404 shape. This is response minimization, not constant-time or traffic-analysis resistance. Rate limits, exact Origin/CSRF and approved-device requirements remain. Endpoint scans can still measure timing; authorized peers already know IDs from signed rosters.

Tests: unrelated known UUID vs random UUID; token tamper, target swap, expiration/revocation; own first-device approval and real native/browser MLS; historical certificate lookup after peer account disable; full backend regression. Exact original certificate strings/public-key bytes and signed histories are preserved. No historical certificate is rewritten or removed. See [results](adversarial-test-results.md).
