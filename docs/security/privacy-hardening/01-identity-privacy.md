# Identity and local profile privacy

**IMPLEMENTED_AND_TESTED.** Original weakness: `serializers.Redeem` required a display name and `ui.tsx` stored the complete six-field account response under `haven-local-user`. The old cache revealed human names, usernames and administrative role to a locked-browser observer and supplied stale profile/role state during offline reload.

Changes: `apps/api/core/serializers.py` accepts omitted/blank display name and username at invitation redemption. `views.Redeem` generates `h_` plus 128 OS-CSPRNG random bits when the handle is omitted. An explicitly username-bound invitation still requires its intended username. Existing handles/password validation, uniqueness, roles, recovery and session binding are preserved. No existing account is renamed. A random handle is displayed for saving after registration; this is an account identifier, not an anonymity claim.

`apps/web/src/app/ui.tsx` removes the legacy cache on startup and writes only `haven-account-id`, a UUID unlock locator. Offline reload constructs a non-administrative placeholder; server authority never comes from that pointer. The locator is needed before decrypting a vault and avoids an unlock dependency loop. Logout, authentication rejection and disable clear it; account-request generations reject stale bootstrap/login results after account switching/logout. Locked profile rendering hides account names/handle and clears notices/errors. Theme/language and optional preferences remain ordinary non-secret localStorage values. IndexedDB account indexes still reveal the account UUID and coarse storage activity.

Contact labels remain in encrypted `VaultState.contact_names`, available after unlock only. Login/account-facing Me still needs its own profile/role; administrative listing now reads only id, username, role and is_active and does not SELECT password/name/recovery fields.

Evidence: `test_registration_needs_no_human_name_or_chosen_handle`; `test_privacy_hardening.py`; real browser `privacy-hardening.spec.ts` and `session-hardening.spec.ts` cover startup cache removal, locked storage, preference restoration, offline reload/unlock, inactivity/pagehide and confirmed logout. See [executed results](adversarial-test-results.md). Names in memory while signed in/unlocked, user-chosen identifying handles, and host/origin compromise remain outside this protection. No schema rewrite of human names, signing key change, vault clear or pending-send deletion occurs.
