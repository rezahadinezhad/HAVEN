# Private contact introduction and sharing

**IMPLEMENTED_AND_TESTED.** `contact-link.ts` previously required `name`; `connect.tsx` populated it from account display_name/username. Shared links now omit that field by default. Older cards with a name still parse; names render as React text and the local label is chosen at verification. The device UUID/fingerprint remain necessary for intended-device comparison and identify a browser.

A new, authenticated `POST devices/contact-introduction` mints a standard Django timestamp-signed bearer grant, salt `haven/contact-introduction/v1`, scoped to exact device, per-device introduction_generation and deployment restore epoch. It expires after 86,400 seconds, accepts at most 512 characters and is carried to lookup/claim in `X-Haven-Contact`, never as an API query string. Contact fragments carry it for deliberate sharing; they remain exposed to sharing applications, clipboard, screenshots, browser history and same-origin code. The UI warns in EN/FA and clears consumed fragments before account bootstrap. Default links contain no real name or private key.

A grant is reusable for its lifetime, because sharing a browser introduction differs from one-use account signup. It does not name a recipient, create a persistent relationship record, authenticate the human sender, replace fingerprint comparison, or authorize group membership. `DELETE devices/contact-introduction` increments the issuer device generation and invalidates all its outstanding grants. Device revoke/recovery/account disable also prevent new first-contact authorization. A holder can forward the link until expiry/revocation; the warning is explicit. The existing signup Invitation still uses its one-time hashed token, row lock, expiration, owner-scoped revocation and quota/audit enforcement. Revoking a signup invitation does not revoke independently shared contact introductions; the UI provides separate actions.

Advanced group/trust lookup now accepts a friend link (or an already-authorized device UUID) through the same scoped contract and verifies its fingerprint before presenting the existing independent verification controls. First-contact grants are kept in component memory only and passed to `Messenger.changeMember` for the KeyPackage reservation. They are not inserted into MLS credentials, certificate pins, signed headers, vault snapshots, durable outbox bodies or logs. Already reserved package/control retries retain the existing exact signed request workflow. A consumed link is not silently trusted: an independent full fingerprint comparison remains mandatory.

Legacy bare-UUID links to an unrelated peer require a fresh link; already-related contacts and historical certificates continue to work. This deliberate API tightening is suitable for the owner's no-real-user/coordinated-upgrade constraint. No mandatory outside provider is introduced.

Restore: a DB rollback can reset the revocation counter. Before reopening a restored DB, set a fresh random `HAVEN_CONTACT_LINK_EPOCH` across API processes; old grants then fail without rotating account/session/signing identities. This is an operator recovery fence, not automatic detection of arbitrary DB rollback. See [migration runbook](migration-and-recovery.md).

Evidence: backend expiry/swap/revoke/restore-epoch tests and real first-chat UI test exercise invitation, fragment clearing, fingerprint comparison, bidirectional MLS delivery, link parsing negatives and pin changes. [Results](adversarial-test-results.md).
