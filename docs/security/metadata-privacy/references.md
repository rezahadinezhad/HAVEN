# Primary sources reviewed and applicability

Reviewed 2026-11-01–02. These are engineering foundations, not a claim of compliance certification or third-party review. Conclusions about HAVEN are based on this repository and are our application of these sources.

- [RFC 9420, PrivateMessage content encryption](https://www.rfc-editor.org/rfc/rfc9420.html#section-6.3.1): established MLS padding is encrypted/authenticated by the protocol. Use the pinned OpenMLS `padding_size` configuration, not a custom cipher, nonce scheme or plaintext trimming. Device trust, outer signatures and atomic ratchet persistence remain HAVEN integration responsibilities. Forward secrecy and post-compromise security have compromise/deletion assumptions; no new proof is claimed here.
- [RFC 9750, security/privacy architecture](https://www.rfc-editor.org/rfc/rfc9750.html#section-8.4): distinguish Authentication/Delivery Service roles, stable credentials and network observations. Its discussion of client-assisted metadata containers does not erase HAVEN's asynchronous roster/ACK/accounting requirements. Transport confidentiality protects different observers from endpoint E2EE. Central signed roster history still reveals membership; anonymous credentials alone do not yield network anonymity.
- [NIST Privacy Framework](https://www.nist.gov/privacy-framework) and [disassociability](https://www.nist.gov/itl/applied-cybersecurity/privacy-engineering/collaboration-space/focus-areas/disassociability): inventory purpose/association/lifecycle per field, eliminate unused timestamps and expired identity links, publish predictable retention and manageable optional activity. Maintain explicit residual risk rather than deterministic identifier hashes marketed as anonymity.
- [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html): exclude tokens/keys/payloads and unnecessary personal identifiers, bound and protect operational diagnostics. Existing supplied logging restrictions are preserved; new worker failure telemetry is static and aggregate. Root/host-added tracing remains outside application enforcement.
- [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) and [Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html): retain secure scoped cookies, expiry/revocation and per-request/device/membership checks; opaque mailbox addresses are not authorization. Do not replace them with unrestricted bearer delivery for privacy appearances.
- [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html): minimize stored data, use established authenticated constructions and explicitly define key custody. No additional encrypted field is added when the same graph remains visible in signed proof JSON and the online server must access its key. Disk/database encryption is not A4 protection.
- [SimpleX chat](https://github.com/simplex-chat/simplex-chat), [SimpleX message queue implementation](https://github.com/simplex-chat/simplexmq) and [SMP protocol](https://github.com/simplex-chat/simplexmq/blob/master/protocol/simplex-messaging.md): recipient-controlled unidirectional queues and separate authorization keys inspire the research comparison. HAVEN cannot import different ACK retention, pairwise identity or resource-accounting semantics without proving compatibility with its MLS group ordering/device model.
- [Signal sealed sender](https://signal.org/blog/sealed-sender/): sender certificates/delivery authorization illustrate replacing both spoofing and abuse controls when hiding the outer sender. HAVEN's signature/roster/quota surfaces require a new protocol before doing that. Correlating issuance/transport remains a concern.
- [RFC 9474 blind signatures](https://www.rfc-editor.org/rfc/rfc9474.html): standardized primitive is not an anonymous queue authorization, quota/refund, revocation or recovery protocol. No experimental implementation is introduced; audited library/application review would be required.
- [Communication–Computation Trade-offs in PIR](https://eprint.iacr.org/2019/1483): supports considering private retrieval alongside concrete computation/communication costs. Does not protect sender submission, authenticated account association or traffic patterns, and supplies no HAVEN measurements.
- [Katzenpost specifications and threat-model entry point](https://katzenpost.network/docs/): independent mix architectures require additional transport/trust/traffic assumptions. No mandatory foreign relay, new domestic proxy chain or perpetual cover traffic is justified for this emergency-connectivity base deployment.
- [Merged PR #18](https://github.com/rezahadinezhad/HAVEN/pull/18): connector retrieved the merged diff and metadata and local git confirmed HEAD `0240706`. Reviewed message quarantine, segmented vault, quotas, login admission, polling/receipt versions, proof projection and signed pagination. Those pre-existing fixes remain; they are not relabeled as new work.

Firefox harness note: the [Mozilla persistence test discussion](https://bugzilla.mozilla.org/show_bug.cgi?id=1837282) documents the browser’s storage-prompt testing preferences. They are used only in disposable QA profiles after a direct probe observed the real prompt remaining pending despite Playwright permission grants. Native IndexedDB and cryptographic paths are not mocked; no TLS preference or certificate check is relaxed.
