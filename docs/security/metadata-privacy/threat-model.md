# Threat model and assurance boundaries

Assets: message/media plaintext and keys; account/device/contact identity; graph, sequence, size and timing; enrollment/recovery/consumption records; availability, ratchet continuity and durable delivery. Trust assumptions: honest verified clients, uncompromised browser/runtime while unlocked, approved-device fingerprint comparison, correct OpenMLS integration, uncompromised TLS/client trust roots, PostgreSQL durability, and explicit backup custody. A1 excludes application secrets and endpoint vaults. A2 assumes readable/decrypted backups; archive encryption helps only while its key is unavailable. This is an analytical model and regression evidence, not a formal cryptographic proof.

## Preserved invariants and analytical checks

Padding changes OpenMLS local framing configuration only. Existing known legacy configuration is upgraded on encrypt; a different unrecognized configuration is rejected rather than replaced. Maximum application plaintext remains 131072 UTF-8 bytes. MLS adds authenticated zero padding and parses it; HAVEN neither invents an envelope cipher nor strips trailing plaintext. Config migration occurs inside speculative state returned to the existing atomic vault/outbox workflow. Already queued ciphertext and signatures are retried unchanged; the backend does not require padding, so an old sender is interoperable but leaks finer lengths.

No changes to signing keys, cryptographic suite, nonces, credential pins, epoch authentication, roster policy, chain hashes, request digest or durable-before-ACK ordering. New schema drops never affect signed bytes or resource charges. Active KeyPackage claims remain retryable until expiry and are still checked during Add. Digest tombstones continue rejecting reuse even after device=NULL. Attachment cleanup rechecks eligibility after the completion/claim row lock. The notification projection preserves its routing and at-least-once transaction semantics.

Tests demonstrate selected implementations and failures; they do not prove global fork detection, eliminate database rollback, establish production capacity or provide a third-party review. The [final report](report.md) distinguishes executed checks from untested host/physical/network properties.
