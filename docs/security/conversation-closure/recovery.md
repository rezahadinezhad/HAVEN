# Migration, rollback and restore

Migration `0019_experimental_conversation_closure` adds four tables: the conversation's closure state/artifacts, opaque retired conversation markers, keyed retired device/message markers, and a single permanent replay-key commitment. It modifies no legacy conversation, credential, envelope, ciphertext or signature. The migration's final irreversible operation refuses reversal **before any new table is dropped**. An explicit forward-recovery deployment is required after closure or retirement exists.

The existing notification SQL login receives no access to these tables; its real PostgreSQL privilege test includes all four. Migration owner/runtime/backup access remains sensitive. The metadata inventory now classifies 206 current and eight removed fields.

Before reopening any restored database, change `HAVEN_CLOSURE_EPOCH` to a fresh valid namespace (`[A-Za-z0-9_-]{1,128}`). Old opted-in conversations then remain read-only; do not rewrite their signed genesis to adopt the new namespace. Retain their local final certificates and use independently verified recovery/reconciliation. Existing contact-link restore-epoch procedures still apply separately.

A retired group requires permanent denial of its old conversation ID, MLS group ID and sender/message ID tuple. Keyed markers use an independent random replay secret of at least 48 characters, unequal to API/routing secrets. This key is deliberately absent from normal deployment configuration because production retirement is disabled. Synthetic fixtures supply their own value. The permanent key commitment rejects accidental key replacement; missing binding with existing markers also fails closed. Never rotate/drop the replay key or markers as ordinary retention cleanup. Account/device credentials are neither reused nor deleted by retirement.

Database namespaces and marker keys are operational fences, not an external monotonic ledger. An old backup may still contain the entire graph, finality may roll back, and an attacker controlling SQL plus every client backup can undo server-only evidence. Production activation requires an independently reviewed external checkpoint/restore strategy. Old code that ignores closure state is not a safe rollback writer: fence traffic and recover forward rather than restoring an old binary into a finalized database.

Archive export is encrypted under the vault unlock passphrase at export time, with account/conversation scope binding. Store that passphrase separately. Restore accepts finalized complete text archives for the same account, verifies their signatures and commitments offline, and refuses conflicting existing archives. It never restores live device keys. Full account recovery already creates a fresh MLS identity; copied closure archives remain local history. Normal history import does not silently import new live authority. Clearing delivered ordinary chat history preserves closure archives.

No backup, WAL segment, replica, provider copy, client export or real history was destroyed by this work. Existing running deployment containers were not upgraded. Only the isolated local evaluation database received the additive migration; destructive runs used separate pytest databases that were explicitly marked and later dropped.
