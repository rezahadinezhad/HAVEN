# API and delivery contracts

`packages/contracts/openapi.json` is OpenAPI 3.1 generated from runtime request serializers plus explicit public response schemas by `scripts/generate-contracts.py`. `apps/web/src/lib/generated/schema.ts` is generated with pinned openapi-typescript; `client.ts` exposes typed operations. Regenerate both together. Representative response contracts are exercised in core/tests/test_contracts.py; broad response fuzz/compatibility qualification is outstanding. WS types are in ws.schema.json and the client validates emitted hints with Zod.

All application requests use same-origin `/api/v1`, secure opaque cookie sessions, exact Origin and CSRF on mutations. No public contact directory. A known opaque device ID can be looked up without consuming a KeyPackage using GET; claiming a package uses POST and CSRF (a deliberate correction to the specification's mutation-via-GET example). Clients independently compare fingerprints; delivery-server assertions alone are not peer trust. Revoked/pending credentials are readable only by their own account or current members of a shared historical group, solely for historical verification. The atomic claim path still requires an active approved target.

MLS controls and application envelopes carry signed RFC8785 headers with conversation/group IDs, sender, stable client ID, epoch, sequence, previous chain hash, ciphertext hash and optional full roster/role transition. Genesis is independently signed. The native public-only verifier checks official public MLS structures and credentials. It cannot decrypt content. Acceptance is committed in PostgreSQL before ACK; a transactional outbox later emits optional WS hints.

`proofs?after_seq=` returns signed public history, including prejoin control/header metadata without old ciphertext. `messages?after_seq=` is device-membership scoped and begins at the device's join point; it does not give a new device old encrypted message history. Existing clients validate signed delta proofs anchored to their retained genesis/chain checkpoint; new/legacy checkpoints validate the full signed history. Pages are bounded by the captured server sequence so concurrent new envelopes wait for the next synchronization. Sequencing is per conversation; client message UUID is the stable idempotency key. Lost ACK retry preserves ciphertext; conflicting epochs require explicit recipient review/resend, never silent re-encryption. Authorization is rechecked on idempotent retry.

No server plaintext search exists. Read receipts are encrypted opt-in application events; transport ACK means recipient synchronization only. Typing is optional, ephemeral server-visible metadata. WS hello/heartbeat/resume/sync.required/ephemeral.typing are implemented; other reserved schema names are not emitted feature claims. HTTP jittered polling remains authoritative if WS is blocked or Redis fanout fails.

Attachment init is idempotent by client-generated opaque UUID and declared bounded shape; chunks are unique and hash checked, at most 512 KiB+16 bytes for client-produced chunks. Server stores neither raw name/MIME nor content key. Complete validates total bytes/chunks. Authorized download still verifies AEAD in browser. Revoked/removed members cannot download through the API, but cached prior plaintext/ciphertext cannot be erased remotely.

Normal settings return CRYPTO_NOT_READY on gated device/crypto/conversation/media paths. The loopback integration profile executes them for real. Admin status is operational metadata; no decrypted-content endpoint exists. Backup/release records are operator assertions with hashes, not independent signature/restore/audit verification.

## Minimal retention

Authenticated `GET /api/v1/privacy-policy` reports the actual policy shown in Settings. Message reads requesting retired application ciphertext return HTTP 410 `history_retired_use_verified_fresh_device`; the client must not skip ratchet history. Proofs and idempotent acceptance remain available. `Envelope.ciphertext_retired` distinguishes retired payloads; `received_at` is nullable. View-once public request/response contracts are unchanged; its internal consumption ledger no longer stores permanent opening timestamps. See docs/security/server-data-retention.md.

## Guided friend connections

`GET /api/v1/invitations` returns only the current user's invitation capability, denial reason, next UTC reset and own pending IDs/expiries. `POST` takes the existing invitation request shape and returns a one-use token once; only its hash is stored. Approved proof-bound members need the crypto gate open, member issuance enabled, fewer than three issues today and fewer than three pending invitations; their maximum expiry is 24 hours. User-row locking and invitation-created audit records serialize the daily limit even after consumed invitation cleanup. Administrators retain the existing 72-hour upper bound and admin endpoints. All creation is subject to the global pause and ten-per-minute request limiter. `POST /api/v1/invitations/{id}/revoke` can revoke only the caller's own invitation; retries are idempotent and do not append repeated audit records. All endpoints require authentication; writes retain Origin and CSRF checks. No privilege is granted through inviting.

A friend card uses a versioned public device ID, full SHA-256 fingerprint and name in a same-origin HTTPS URL fragment. It is parsed locally, not stored in a new server-side contacts directory. Existing known-device/key-package endpoints resolve the specific public credential; matching a link is insufficient to pin it. Explicit independent code comparison is mandatory before the guide pins/creates/joins the chat. Incoming participants use the same verification step. The OpenAPI contract and generated TypeScript schemas include these new paths and policy fields.
